# Pool World v8.5 — idle canvas render invalidation (26 October 2026)

## Scope and limitation

This development-only change addresses measured **unnecessary redraw work while the balls are stationary**. It does **not** establish that active ball motion is smooth on a physical Samsung Galaxy A37, and is not human gameplay acceptance. The user continues to report weak/jerky feel; that remains a release blocker.

## Reproduced defect

The original `frame(t)` always called `render()` on every requestAnimationFrame, even with no balls moving and no input changes. The full 1100×570 canvas, premium table, 16 ball shells and gradients, and aiming guide were repainted 60 times per second when nothing had changed.

New mandatory browser regression: `tests/test_pool60_render_invalidation.py`, commit `0ef56fb257098f81de4cac49afdd3087becaeae2`; workflow registration commit `9c2412394ac25970c92ab291b1e475a6b242357b`.

Four viewports: 390×844, 844×390, 768×1024 and 1366×768. Baseline workflow #213, run ID 40269543418, **FAILED intentionally**: 28/36 new checks passed, eight actual idle-redraw failures. Each viewport repainted 120 times over 120 idle frames, with measured Chromium canvas CPU time over those 120 frames of 53.6, 59.1, 77.4 and 81.0 ms respectively. Each also repainted all 30 frames after aim had stopped moving.

## Code correction

Candidate gameplay commit `ecb66bb30ffe77a078fdc747efa49f857b4fc635`, candidate blob `ede1bde23722cf57dbb1cd9b225980cf4fa47ebc`.

Added a `renderDirty` invalidation flag. During active shots the game still draws every animation frame. During idle it paints the initial scene once and skips unchanged full-canvas redraws. Actual pointer aim, keyboard arrows, guide toggles, rack reset, shot completion, ball-in-hand changes and interrupted pointer gestures mark the scene dirty so the next frame repaints. Existing immediate fine-aim rendering is preserved. Fixed-step 120Hz physics, shot power, four approved audio data URIs and all match rules remain unchanged.

## Remaining critical work

Measure actual browser frame-time p50/p95/p99 and input-to-display latency **during a moving full rack**. Profile expensive drawBall gradients and physics allocations before optimizing them. A reduced idle CPU budget is useful but **does not prove** that moving balls are smooth, that shots feel powerful, or that 60fps is sustained on the Samsung. Obtain independent physical-device/human acceptance before any production release.
