# Pool World v9.6 — 120Hz contact-object reuse (26 October 2026)

## Scope and safety
Development branch `development/poolworld-match-engine` only. Production `main/index.html` remains unchanged at blob `011657038a72ff255297ca78f595eef0e67df1e3`. No changes to monetisation, multiplayer, content, or approved audio. Physical Samsung Galaxy A37 and human acceptance have **not** occurred; the game remains release-blocked.

## Reproduced defect
The previous v9.3 contact-list reuse removed temporary arrays but still constructed a fresh `{a,b,t}` object for every overlapping pair at every 120Hz physics tick. New mandatory `tests/test_pool60_contact_object_pool.py` was committed as `dd90f3fe0f25205d81211a0e329a349e6f7d708e` and registered in CI at `2257a1c7abe7fb1d46d2fa2050fd9650b2e01c4d`. Baseline run #268 (40351089065) **FAILED 44/64 checks**, 20 genuine failures over four viewports.

Across each viewport, 64 repeated two-ball contacts allocated 64 distinct records; 40 overlapping three-ball clusters allocated 120 records; and 72 active full-rack frames allocated 26 records, despite a maximum of seven simultaneously active contacts. An empty tick did not preserve any contact-record identity for subsequent hits.

## Gameplay fix
Staging candidate commit `a24925dc5984eec3544bcb6cf47efe0108b1c3f0`, blob `17ce8d0c0656002b10153be31f3299152c13c99d`. A bounded `contactPool` retains one record per active contact-list slot; each tick rewrites its `a`, `b` and `t` fields before the existing sort and impulse solver. The active `contacts` array still resets per tick and retains its legacy array API. Collision ordering, energy caps, shot power, pocket rules and all four approved v3.9 audio data URIs are unchanged.

Across all four viewports, repeated two-ball contacts now use **one** record for 64 contacts (63 allocations avoided), three-ball clusters use **three** records for 120 contacts (117 avoided), and the full-rack sequence uses **seven** records for 26 contacts (19 avoided). Reuse survives quiet ticks; positions/velocities remain finite and balls stay on cloth.

## Limitations and next work
The results demonstrate fewer JavaScript allocations, **not** a causal improvement in phone frame rate, physical touch-to-display latency, or user-perceived smoothness. Next, capture actual Chromium active-shot requestAnimationFrame p95/p99 frame pacing, GC pauses and pointer-to-visible response; add mandatory reproducing tests for any demonstrated user-visible defect. Preserve the development-only gate and require real Samsung/human acceptance plus explicit owner approval before production.
