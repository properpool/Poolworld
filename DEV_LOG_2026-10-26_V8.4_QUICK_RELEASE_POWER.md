# Pool World v8.4 — fast-release shot-power correction (2026-10-26)

## User-visible defect
The user reports weak shots and poor smoothness on a physical Samsung Galaxy A37 using the development preview, not production. Physical Samsung/human acceptance is still unavailable. This change addresses a reproduced, specific fast-release power-control failure; it does **not** establish that overall gameplay feels good or runs at 60 FPS on the phone.

## Reproduction before the fix
A new mandatory Chromium browser-input regression, `tests/test_pool60_quick_release.py`, uses genuine pointer press/release coordinates with **no intervening pointermove**, across four viewports: 390x844, 844x390, 768x1024, and 1366x768. It also tests a long pull returned to its starting point.

Baseline workflow **#208**, run ID **40264577971**, on commit `fedff7703f2b7a1ac52c428e68223b0cb62b6557`, **FAILED**: 20/32 new checks passed; 12 failed. All four viewport sizes reproduced the same defects:
- A 45%-track immediate release fired at **4.9602** speed units instead of expected **7.2512**.
- A 60%-track immediate release also fired at **4.9602**, instead of expected **9.1462**.
- Returning a long drag to its starting point left an unintended power setting around **26.923%**, instead of restoring the previous **45%**.
These are actual browser-input release coordinates and cue-ball initial velocities, not merely a standalone shotSpeed() unit test.

## Gameplay correction
Gameplay candidate commit `67a957b2497ebf9063e40705035c1377db7d6654`, blob `4b5bd84d2ecfcd5a6e48fee3f4e22e6ef25cca6a`:
- Uses final pointerup coordinates to calculate power before firing, even when no intermediate pointermove event was delivered.
- Tracks whether a pull actually moved; if it returns to its starting position, restores the original power rather than retaining an unintended selection.
- Preserves ordinary tap-to-select, intentional partial power adjustment, deliberate pull-to-shoot, cancellation/lost-pointer-capture safety, and the separate SHOOT button.
