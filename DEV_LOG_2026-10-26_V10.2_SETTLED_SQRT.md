# Pool World v10.2 — settled-shot hot-path regression (26 October 2026)

## Problem and reproducible baseline
The animation callback checks `settled()` while balls are moving. Previously it used `balls.every(b => b.potted || Math.hypot(b.vx,b.vy)<.022)`, creating a callback and calculating up to sixteen square roots every rendered frame, even for balls with zero velocity. This is unnecessary for comparing against a fixed positive speed threshold.

Mandatory regression: `tests/test_pool60_settled_sqrt.py` (commit `d0518ae2bd9fbff08e66ba079ec37b44df2127ee`), registered in the push workflow (commit `41ff0325894aa6a5e870d2650088ed3a6d5af13a`). It checks 240 settled queries on a 16-ball stationary table and speed thresholds, diagonal velocities, potted balls, NaN and Infinity across 390×844, 844×390, 768×1024, 1366×768. It also records actual headless Chromium moving-rack rAF callback p95/p99 frame gaps and frame-function CPU duration. These diagnostics are not physical-device measurements.

## Gameplay fix
Staging commit `195c3f59f9cac0c93aa9fefdabffd1c0fc798aa5`, Git blob `4fce844221a8d097ad2a8c1c3da73dbc9061a2e3`:
- Use `SETTLE_SPEED2=.022*.022` and compare squared velocity magnitudes without `Math.hypot` or `Array.every`.
- Preserve the original strict threshold: a speed exactly 0.022 remains moving.
- Explicitly use a negated comparison to preserve NaN and Infinity as *not settled*; ignore potted balls.
- Do not change shot impulse, ball dynamics, six-pocket rules, visuals or audio.

The fixed build returned **zero Math.hypot calls** across 240 settled queries on 16 stationary balls in each viewport, compared with 3,840 calls in the old implementation. The new 60-check suite passed **60/60** on candidate CI **#306** (run ID `40405352746`), alongside all existing suites and approved audio-source integrity. CI jobs and decoded logs inspected.

## Browser diagnostics (candidate CI #306)
Across the four viewports, actual headless Chromium recorded 38–39 moving-rack rAF callbacks over ~650ms. Frame-gap p95 was 16.7ms (p99 16.7–16.8ms); measured frame-function CPU p95 was 0.8–1.2ms and p99 0.9–1.9ms. These measurements are descriptive only; they do not prove a causal speedup from this small optimisation, nor do they measure the Samsung Galaxy A37's GPU, display, touchscreen-to-photon latency or subjective shot strength.
